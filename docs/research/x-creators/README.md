原作者写“去重后约 119 位”，但按正文 Handle 实算是 **111 个唯一账号**。批量分析应以 111 为基数，并把领域设计为多值标签，而不是为重复出现的账号重复生成档案。

## 三、本次是如何获取、解析和总结的

### 1. 获取推文

本次实际链路是：

`原始 X URL → X oEmbed → t.co 短链接 → X Article ID → 公开兼容接口 JSON`

1. 调用 X 官方 oEmbed，确认作者、原帖地址、日期和嵌入正文。
2. oEmbed 只返回 `t.co` 链接；跟随 301 跳转，得到 X Article ID。
3. 当前环境没有可用的已登录浏览器会话，X Article 匿名页面返回 404，因此使用 FxTwitter 公开兼容接口读取公开帖子的 Article JSON。
4. 从 `tweet.article.content.blocks` 提取标题、段落和列表。

FxTwitter 不是 X 官方源，只应作为传输层的降级方案。正式批量生产应优先使用 X 官方 API、授权浏览器会话或自有合规采集器，并缓存原始响应。

### 2. 解析与清洗

| X block 类型          | Markdown/结构化结果 |
| --------------------- | ------------------- |
| `header-one`          | 领域标题            |
| `unstyled`            | 普通段落            |
| `ordered-list-item`   | 博主记录            |
| `unordered-list-item` | 条件或说明          |

清洗过程包括：去除空 block、保留原序；从名单末尾抽取 Handle；Handle 转小写去重；保留账号出现过的所有领域；把“原文评价”和“研究结论”分开。推荐的数据主键和字段是：

`Handle → 原文分类 → 主页资料 → 代表帖证据 → 自有产品 → 商业化证据 → 五维结论 → 置信度 → 核对日期`

### 3. 代表作如何选择

代表作不是机械选择点赞最高的帖子，而是优先选择：

- 能代表长期方法论，而非一次性热点；
- 与赛道、产品或商业闭环直接相关；
- 有稳定 URL，可回看原文；
- 尽量覆盖观点、案例、产品三类证据；
- 金句能定位到具体帖子或官网，不能把转述伪装成原话。

批量方案可为每人召回最近 6—12 个月的 20—50 条候选帖，再按主题相关性、互动量、时间衰减和证据价值排序，选出 3—5 条代表作。互动量只辅助排序，不能替代内容判断。

### 4. 五维总结方法

| 维度     | 回答的问题                 | 主要证据                           |
| -------- | -------------------------- | ---------------------------------- |
| 赛道     | 长期解决什么问题、面向谁？ | 主页、长期主题、官网               |
| 打法     | 如何获客、建立信任和转化？ | 内容格式、节奏、CTA、流量去向      |
| 金句     | 哪些原话最能代表方法论？   | 可回溯的帖子或官网原文             |
| 产品     | 实际拥有或运营什么？       | 官网、产品页、代码仓库、本人声明   |
| 盈利模式 | 钱从哪里来，哪些只是推测？ | 价格页、会员页、广告/订阅/服务证据 |

写作采用“事实—原话—分析”三层：公开页面可直接证明的是事实；带出处的表达是原话；跨证据归纳出的路径标明为分析。收入规模、产品所有权和收入占比没有直接证据时，不写成确定事实。

### 5. 质量检查

- 五个维度必须齐全；
- 金句尽量附来源链接；
- 自有产品与第三方推荐严格分开；
- 重新统计领域、列表和唯一 Handle；
- 保存核对日期；
- 格式检查并抽查链接；
- 暂时不可访问的链接要区分超时、登录墙和真正下线。

## 四、可复用性评估

结论：**可以复用，但名单解析可高度自动化，产品归属、盈利模式和代表作判断不能完全自动化。** 推荐“机器批量采集与初稿 + 分层人工复核”。

| 环节           | 可复用性 |   预计自动化 | 主要限制                     |
| -------------- | -------- | -----------: | ---------------------------- |
| 名单解析与去重 | 很高     |         95%+ | Handle 改名、正文格式异常    |
| 主页与外链采集 | 高       |      80%—90% | 登录墙、限流、保护账号       |
| 候选代表帖召回 | 中高     |      70%—85% | API/搜索可用性、旧帖缺失     |
| 赛道聚类       | 高       |      80%—90% | 跨赛道账号容易被单标签化     |
| 金句抽取       | 中高     |      70%—85% | 上下文截断、转述混淆         |
| 自有产品识别   | 中       |      60%—80% | 创始、任职、投资、推广难消歧 |
| 盈利模式判断   | 中低     |      40%—70% | 公开收入证据不足             |
| 五维初稿       | 高       |      80%—90% | 依赖上游证据完整度           |
| 最终事实核验   | 中       | 不建议全自动 | 需处理冲突和隐含归属         |

推荐流水线：

`名单去重 → 账号任务表 → 并发采集主页/帖子/官网 → 代表作排序 → 产品实体消歧 → 五维初稿 → 引用与事实校验 → 统一编辑`

每个账号保留 `待采集 / 证据不足 / 待复核 / 已完成 / 需更新` 状态。证据不足时应降级为短档案或进入人工队列，不能为了填满模板而编造产品和盈利模式。

复用前建议补强六点：稳定采集层和降级策略；给每项结论建立证据表；做产品实体消歧；以 Handle 建主表、领域做多值标签；支持增量更新；首批抽样 10—15 人测量错误率。

总体评分：用于快速建立博主地图 **8.5/10**；形成可复查商业档案 **8/10**；精确判断真实收入 **5/10**；完全无人值守地产出 111 份高可信报告，**不建议**。

### 三种生产方案（剩余 108 人）

| 方案             | 档案深度                     |                       总工作量 |    4 路并发墙钟时间 |
| ---------------- | ---------------------------- | -----------------------------: | ------------------: |
| 快速扫描         | 每人 1—2 条证据、短结论      |                     14—22 人时 |       约 1 个工作日 |
| 标准档案（推荐） | 当前五维深度、3—5 条代表作   | 36—63 人时 + 6—10 人时总编质检 | **约 2—4 个工作日** |

估算假设：采集接口稳定、任务按唯一账号拆分、4 路并发、最后统一质检。X 限流、登录墙、失效链接、同名产品和商业证据不足会增加时间。稳妥执行方式是先用半天试生产 10—15 人，评估错误率后，再用 2—4 个工作日完成标准档案。若只让模型快速总结而不核验，虽然更快，但会系统性高估产品归属和盈利确定性。


[SEO.Box 收入目标拆解计算器](https://seo.box/calculator/money/)把“月入多少美元”拆成网站数、关键词数、流量、排名、外链预算与回报率。这类工具的作用不是做绝对准确的预测，而是帮助用户把模糊目标转成运营指标。

他经常公开网站流量、AdSense 收入、关键词与成员案例。这能显著提升内容的说服力，但读者需要区分“方法可复用”和“个案收益可复制”：个别项目的收入不代表普遍结果。

这句话概括了其最核心的产品方法：从已存在的搜索需求出发，而不是先做产品再猜用户是否需要。来源：[新网站首日流量复盘](https://x.com/gefei55/status/1773541415521533961)。

他常把收入目标拆成订单、流量和转化率，让大目标变成可计算的问题。来源：[收入目标拆解](https://x.com/gefei55/status/1874286449534890403)。

这句话反映了他对独立开发的基本判断：需求研究和分发能力比灵感更重要。来源：[免费教程的意义](https://x.com/gefei55/status/1784075404770521255)。

#### 2. 打法
